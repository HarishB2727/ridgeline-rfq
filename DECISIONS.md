# Decisions

Dev inbox, 24 emails, regenerated by `rfq parse`:

| | |
|---|---|
| silent losses · hallucinated lines · lost · phantom | **0 · 0 · 0 · 0** |
| classification | 24/24 |
| line items | P 100% · R 100% (210/210) |
| paired fields | uom 100% · source 100% · context carried 100% · **qty 99.1%** |
| `revises` / `duplicate_of` | 100% / 100% |
| `needs_review` | P 1.0 · R 1.0 |
| cost | $0.2882 cold · $0.0120/email · $0.0000 and 0 calls on re-run |

Treat those with suspicion. I iterated against this key five times; see *Predictions* below for
what I actually expect.

## The shape of it

**Code decides everything checkable; the model decides only what requires reading; nothing the
model says ships without being verified against the source.**

Code owns: MIME, the current-vs-quoted split, routing attachments by magic bytes, hidden
sheets, text-layer-vs-scan, the uom vocabulary, de-duplication, duplicate and revision links,
every `needs_review` rule, and the groundedness check. The model owns: which of seven classes,
which rows are items, and which context belongs on which line. Those are reading judgements and
no amount of regex does them.

Between the two sits the thing I'd defend first: **every extracted line's `raw` must actually
occur in the document it claims to come from**, by token coverage rather than substring (a
pasted spreadsheet splits one row across three lines, so substring is too strict). Lines that
fail are dropped. Precision is a property of the system, not a hope about a prompt.

It was not theoretical while building: reading E006's PDF, the model also returned the two
gasket lines that live in the email body, because the body is supplied as ambient context. The
check dropped them, the per-email trace said why, and that told me the prompt was wrong as well
as the output — a sentence pointing at an item held elsewhere is not itself a line. Fixing that
removed the behaviour at source, so **the current run drops nothing on the dev inbox**: all 24
`dropped_lines` are empty. Do not read that as the check being idle; read it as the dev inbox no
longer provoking it. Which also means the guard is exercised by `tests/test_documents.py` and
not by dev, and a verification layer that never fires on the data you can see is one I would
want more evidence for than I have.

The second thing I'd defend: **quoted history is excluded from what the model sees**, not
merely labelled. E012 is a status inquiry with an entire seven-line RFQ pasted underneath;
nothing about it reaches the extractor, so there is no opportunity to hallucinate it, and the
groundedness check would drop it even if there were.

## Something in the data that surprised me

I assumed I could tell a company logo from a document by file size, and wrote the threshold
before looking. In E010 the Delta Mechanical logo is **3,307 bytes** and the screenshot of the
spreadsheet holding six real line items is **4,295**. In E017 the Cobalt Ridge logo is **5,288
bytes** — larger than both. Any byte threshold I would have picked silently deletes a
customer's order, and E017 is precisely the email where losing the attachment is the whole
point of the test.

So every image goes to the vision model and `"decorative"` is an answer it is allowed to give.
It costs about $0.002 to ask a model whether a 4KB PNG is a logo, which is the correct price
for not dropping an order. `looks_decorative()` survives only as a filename hint, used nowhere
that can delete a line.

The second surprise was mechanical. On E009's two-page phone scan, reading a whole page at once
got **13 of 28** quantities right; the same model reading three overlapping horizontal strips
of that same page got **28 of 28**. I assumed a stronger model would fix it and tested that:
`gpt-5` on the whole page scored **14 of 28** — no better than `gpt-4.1`. The failure is row
drift across a tall skewed table, not recognition, and it is fixed by showing fewer rows per
look, not by spending more.

## Something in the README I disagree with

> `needs_review` … Only for `rfq`, `rfq_revision` and `purchase_order`.

This makes the flag unavailable exactly when it is most needed. My resilience test generates an
email with an empty subject, an empty body and one corrupt attachment. There is no evidence of
what it is. The model called it `other` — a defensible reading of nothing — and the rule then
forbids flagging it, so it leaves with no lines and no flag. That is a textbook silent loss, the
failure the same document ranks as the most expensive, produced by following the format.

What I did: when nothing in an email could be read — empty body, every attachment unopenable —
and the headers do not positively say machine-generated (no bounce envelope, no
`Auto-Submitted`, no `List-Unsubscribe`), code overrides the class to `rfq` so the flag becomes
legal, and flags it. I am choosing a possible phantom request over a possible silent loss, on
the same asymmetry the brief sets out. If the grader counts that as a misclassification, I would
rather lose that point than the customer.

A smaller one: *"Not items in quoted earlier messages"* is right nine times in ten and wrong on
E020, where "go ahead with items 1, 2 and 4" names items that exist **only** in the quoted
quote. I kept the rule and gave it three declared exceptions, each detectable from the current
message alone: a message that selects numbered items from the history, one of our own reps
forwarding a customer, and a revision restating an order. Everything else sees no history at all.

## Predictions for the held-out inbox

Dev is saturated and I tuned against it, so I expect a real drop. My honest ranges for ~40
emails:

| | predicted |
|---|---|
| silent losses | **0–1** |
| hallucinated lines | 0–4 |
| lost / phantom requests | 0–2 |
| classification | 88–95% |
| line recall / precision | 93–98% / 96–99% |
| qty | 94–98% |
| context carried | 90–96% |
| `needs_review` recall | 0.85–1.0 |

**The two kinds I expect to get wrong.**

*Photographs and scans of dense tables.* Even after the strip fix, E009 still swaps the
quantities of items 11 and 12 — adjacent rows, 2 errors in 210 lines. That failure mode has not
gone away, it has shrunk. Handwriting worse than dev's, a steeper camera angle, a table with no
item-number column to anchor on, or a multi-column form will push it back up. It will show as
wrong `qty` on paired lines rather than as missing lines, which is the better way to be wrong,
but it is where my numbers will fall first.

*Thread messages that do two things at once.* The classifier picks one of seven labels for a
message that chases a quote **and** changes it, or commits to part of an order **and** asks a
question. Dev has one instance of each in isolation and I get both right; a message that mixes
them has no right answer in this schema and I will pick the wrong half.

I originally listed a second case here — a purchase order that accepts items by description
rather than by number, *"go ahead with the flanges and the pipe"* — on the reasoning that
`selects_items_from_quoted` keys on labels it can name. Then I built it (`S011` in
`tests/test_shapes.py`) rather than leaving it as a guess, and it returns exactly the flange
and the pipe and correctly holds the valve and the gasket. The prediction was wrong. I am
leaving the correction visible because an untested prediction and a tested one are not the
same kind of claim, and most of the rest of this section is still the first kind.

I also expect `vendor_quote` to be my most fragile class. Dev's example is unmistakable — it
quotes our own rep, with prices, lead times and FOB terms. A supplier email without those
tells, or a distributor who is both customer and supplier, would read as an `rfq` and become a
phantom request.

## How this runs for real

**3,000 emails a day by webhook.** The webhook does one thing: write the raw bytes to object
storage and push a job. Workers run the existing per-email phase A, which already shares
nothing between emails and is already thread-parallel. Phase B — duplicates, revisions, the
review flag — needs its thread's history, so it keys on a thread id and runs after, serialised
per thread rather than globally; that is the one piece of today's design that does not scale
as written, because `link_inbox` walks a list in memory. At 3,000/day and $0.012 that is $36 a
day, and the classification gate means the roughly 40% of a real inbox that carries no items
costs a twentieth of that. **Built:** the per-email isolation, the parallelism, the cost
accounting. **Not built:** the queue, the thread store.

**The provider is down for two hours.** Each call retries four times with exponential backoff
and jitter. Past that the email returns flagged with the reason and the run continues — a
two-hour outage produces a backlog of flagged emails, not a crash and not an empty file. What
is missing is a circuit breaker (right now every email pays its own four retries, so the whole
inbox slows to the timeout) and a requeue, so the flagged ones are retried when the provider
returns instead of waiting for a human. **Built:** retries, degradation, the never-crash
boundary — verified by running the whole dev inbox with the key removed. **Not built:** the
breaker and the requeue.

**A 300-page PDF.** Capped at 20 pages (`DEFAULT_PAGE_CAP`), and a document that was truncated
sets `needs_review` naming the file, so nobody quotes two thirds of a job without knowing. Text
documents chunk at ~18k characters on line boundaries with the opening lines carried into each
chunk, because that is where the "unless noted" defaults live; scans go one call per page.
**Built**, though the cap is a blunt instrument — the right version prices the document first
and asks before spending $40 on one email.

**The same email delivered twice.** Two independent mechanisms. The cache is content-addressed,
so the second delivery makes zero model calls and costs nothing. The duplicate rule then marks
it: same sender, same subject once `Re:`/`FW:`/`RESEND:` are stripped, plus content equality by
attachment hash, body text, or extracted line set. E008 is byte-identical attachments under a
rewritten covering note, so the hash does the work there. **Built.**

## What I rejected

**A stronger model instead of better framing.** Measured, not assumed — `gpt-5` scored 14/28 on
the scan that strips fixed at 28/28.

**Defaulting to `gpt-5.x` because the key reached it.** You run the held-out inbox with your
key. If it lacks the model I named, the run dies. I default to models that are broadly
available and whose price I can state, and fall back rather than fail.

**One extraction call per email.** Per document gives correct `source` by construction, bounded
prompts, parallelism, and a failure that takes down one attachment instead of an inbox.

**Regex extraction for the "easy" plain-text emails.** E001 looks parseable until you notice
`4" 150# RF slip-on flange, A105 x 6` puts the quantity last, E002 says "a couple caps", and
E018 is a spreadsheet pasted into plain text with qty, description and size on three separate
lines. A second code path would need all the same judgement and would disagree with the first.

## What I know is broken

- Two quantities in E009 are still wrong (adjacent rows in a scanned table).
- `verify.py` cannot ground a line that came from a picture — there is no text to check it
  against — so image-sourced lines ship on the model's word alone. On the dev inbox that is
  **46 of 210 lines, 22%**: the two phone photos, the scan and the pasted screenshot. Those
  lines get the unit vocabulary, the totals-row filter, the vague-quantity rule and
  de-duplication like any other, but not the one check that asks whether the line exists.
  It is where a hallucination would get through, and the gap I would close next — by asking
  for a verbatim transcription pass first and grounding the extracted lines against that.
- `link_inbox` holds the inbox in memory; fine for 40 emails, wrong for a live queue.
- Item-number de-duplication only engages when the leading numbers look like a contiguous
  index. A strip-split table whose index restarts mid-document would keep a duplicate row.
- The classifier's second-opinion escalation has never fired on real data — it is tested only
  by construction, so I trust it least of anything here.

## What's next, in order

1. Ground image-sourced lines by asking for a verbatim transcription pass and checking the
   extracted lines against it — closes the one place a hallucination can still ship.
2. A held-out-style regression set of my own: perturb the dev emails (re-skew the scans, rename
   headings, shuffle sections) and watch which numbers move. Dev at 100% tells me nothing more.
3. The queue, the circuit breaker and the requeue from the section above.
4. The matcher — designed in `MATCHER.md`, not built.
